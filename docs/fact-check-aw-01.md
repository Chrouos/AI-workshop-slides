# aw-01 正確性檢查

檢查日期：2026-10-29（Asia/Taipei）。範圍：`slides/aw-01/index.tsx` 的 67 頁、對應講稿、引用的數學與小說原文，以及主要產品操作說明。未修改投影片。

這是內容查核，不是版面、文風或程式碼品質審查。「實測」的速度、成功率、模型回覆保留為作者的個別觀察；本次沒有重跑登入、付費 API、本機模型或 Windows 安裝。不能由文件查核替作者證明歷史實測。

## 優先修正

### 01｜P36：工作目錄不是讀檔隔離邊界

- 位置：`index.tsx:2002`；講稿 `3672`，同類說法 `3698`、`3706`。
- 原文：「Codex 只在你所在的資料夾裡讀檔、存檔」。
- 判定：錯誤。Directory 指工作位置；實際可讀、可寫範圍由 sandbox、額外根目錄及權限政策決定。不能把 `cd` 當成只能讀這個資料夾的保證。官方也說 workspace 可包含暫存目錄。
- 建議：「Codex 會以這個資料夾為工作起點；可讀寫範圍由權限設定決定。」保留先 `cd`、再看 `/status` 的教學。
- 來源：[Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)、[Permissions](https://learn.chatgpt.com/docs/permissions)。

### 02｜P44：AGENTS.md 的範圍不只檔案所在那一層

- 位置：`2322`；講稿 `3717–3719`。
- 原文：「AGENTS.md 只管這個資料夾」、「換到別的資料夾就不會讀」。
- 判定：錯誤。專案根目錄到目前工作目錄的指引會合併，父層指引可以在子資料夾繼續有效；另有全域指引與 override。以一層練習資料夾示範可以，但不能據此說換資料夾必然失效。
- 建議：「專案規則通常也適用於子資料夾；更深層的規則可以補充或覆寫。」
- 來源：[Custom instructions with AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。

### 03｜P42：Token 總量漏算輸出

- 位置：`2248–2265`；講稿 `3713`。
- 原文把「提示詞＋讀到的檔案＋前面的對話」畫成「這次用掉的 Token」。
- 判定：錯誤。這只能近似描述部分輸入，還漏了系統／開發者指引、工具定義與結果，以及生成答案和推理所用的 Token。額度也不是只依這三種內容的字數扣除。
- 建議：把等號改成「都是輸入 Token 的一部分」；補一句「生成答案與推理也會使用 Token」。
- 來源：[Reasoning models](https://developers.openai.com/api/docs/guides/reasoning) 的 token accounting；[Pricing](https://learn.chatgpt.com/docs/pricing) 說明額度也受模型、任務大小和複雜度影響。

### 04｜P29：ChatGPT 不必逐檔複製貼上，也能產生下載檔

- 位置：`1813–1819`；講稿 `3635` 起（SameTaskTwoWays）。
- 原文：「你要打開 21 個檔、一段一段複製貼上……再自己存成檔」。
- 判定：對產品能力的描述錯誤。ChatGPT 支援附加檔案，支援的功能與環境下也能生成可下載成品；檔案數與大小仍受限制。P28 講稿雖已提醒可以上傳，P29 又用「要」使必要條件產生矛盾。
- 建議：把左欄標成「手動貼上流程（示例）」。比較重點改為 Codex CLI 能直接操作課堂的本機資料夾，不必先手動附檔與下載回存。
- 來源：[Use ChatGPT](https://learn.chatgpt.com/docs/use-chatgpt)。

### 05｜P52：找到引用原句，不代表整段摘要已被證實

- 位置：`2760`；講稿 `3780–3783`（CheckSource）。
- 原文：「搜得到原句、標題一字不差，才算核對過」；講稿接著說「這段才算核對過」。

- 建議：「先確認引用確實存在，再確認它支持摘要中的每個事件、人物、因果與先後順序。」要核對斬殺成功，還要讀後面的實際行動。標題逐字比對另列一項。

## 概念需要補條件

### 07｜P6、P14：下一個 Token 預測不必然造成隨機性；模型也不是固定機率表

- 位置：`722–729`、`1063–1088`；講稿 `3503`、`3543` 起（WhyHallucinate）。
- 問題：「猜，所以有隨機性」混淆模型與解碼策略；greedy decoding 可以每次挑最高機率 Token。實際機率分布會依上下文動態計算，不是把讀過的文字存成一張固定表，再挑語料中最常見的說法。幻覺也不是只因少一道查證。
- 建議：「模型依上下文計算下一個 Token 的機率；採用取樣時，答案可能變動。生成目標與訓練、資料和評分方式，使流暢不保證正確。」P14 圖上把「機率表」改為「依上下文計算機率」，「挑最常見」改為「依解碼策略選 Token」。
- 來源：[Transformers：Generation strategies](https://huggingface.co/docs/transformers/main/en/generation_strategies)、[Why Language Models Hallucinate](https://arxiv.org/abs/2509.04664)。P8 的機率數字已標示「示意」，這點沒有問題。

### 08｜P12：幻覺不要求語氣肯定，也不限於世界事實錯誤

- 位置：`986–1002`；WhatIsHallucination 講稿。
- 問題：「內容和事實對不上，語氣卻很肯定，就叫幻覺」適合作例子，但定義太窄。輸出也可能違背所提供的文本；說「可能」不會自動使虛構內容變正確。摘要課程尤其需要區分現實事實與對來源的忠實度。
- 建議：「生成了不符合事實，或不受所給資料支持的內容；即使語氣流暢，也可能是幻覺。」另提醒：不是所有任務失敗都宜一律稱作幻覺，算術題也可以直接稱「計算錯誤」。
- 來源：[Hallucination survey，§2.3](https://arxiv.org/html/2311.05232v2)。

### 09｜P13、P18：不能由錯答案或自述，證明模型內部完全沒有計算

- 位置：`1041`、`1398`；RealHallucination、ToolCompare 講稿。
- 問題：GPT-3.5 算出 8402，只能證明算錯，不能證明「它沒有算」。另一張 8460 截圖明確要求「不可以偷偷計算」，也不能拿來代表一般直接回答的能力。模型自己說「純猜」不是內部運作的驗證。
- 建議：P13 改為「直接生成的算術答案可能錯，要用可重跑的工具驗算」；P18 把左欄標成「刻意要求純猜的示例」，若要比較三種方法，需同題同條件的實驗。
- 證據：本地兩張原始圖片已檢視。機制背景見 [GPT-3 論文](https://arxiv.org/abs/2005.14165)、[Reasoning models](https://developers.openai.com/api/docs/guides/reasoning)。

### 10｜P15–18：Thinking 與讓模型寫出步驟，不能完全畫等號

- 位置：`1146–1148`、`1240–1249`、`1399`；CotWhy 講稿「回答前會自動先做一次 CoT」。
- 問題：用 CoT 介紹推理模型可接受，但「一次、回答前、先寫過程」過度限定。推理可以和工具呼叫、可見輸出交錯；顯示給使用者的解題步驟或思考摘要，也不等於完整內部推理。
- 建議：「Thinking 模型會使用額外推理運算，可能分解問題、檢查與調用工具；畫面呈現的是解題說明或摘要。」把提示詞 CoT 和推理模型放成相關但不同的兩件事。現代推理模型通常不必再要求顯示完整思考過程。
- 來源：[Reasoning models](https://developers.openai.com/api/docs/guides/reasoning)、[Reasoning best practices](https://developers.openai.com/api/docs/guides/reasoning-best-practices)、[CoT 論文](https://arxiv.org/abs/2201.11903)。

### 11｜P17–18：確定的是這段加法程式，不是所有 Tool Calling 都沒有隨機性

- 位置：`1325`、`1363`、`1400`。
- 問題：「工具呼叫」不限計算；搜尋、讀寫檔案也都是工具。這段整數加法程式相同輸入可重現，不能推廣成所有工具或整個 Agent 都每次相同。模型仍可能抄錯數字、產生錯誤程式或解讀錯誤結果。
- 建議：「這段加法程式在相同輸入下可重跑驗算；仍要核對輸入、程式與結果。」定義改為「模型請外部程式執行某個功能，再使用回傳結果」。
- 來源：[Function calling](https://developers.openai.com/api/docs/guides/function-calling)；本地計算驗證和確定性限制。

### 12｜P20–24、P50：搜尋、附資料、RAG 的關係要限定

- 位置：`1437`、`1533`、`2600`；WebSearch、OpenBookPage 講稿。
- 問題：「先查再答叫 RAG」作廣義流程可接受，但搜尋必須把查到的內容提供給生成使用，才符合檢索增強；僅叫搜尋工具、或在答案附網址，不足以證明。手動貼一段原文叫提供上下文，不必都叫 RAG；21 回全部讀完做摘要也更接近文件摘要示例，並未示範按問題檢索相關片段的差異。
- 建議：「當系統檢索外部資料，並用那些資料輔助生成，就屬於廣義 RAG。」把大綱練習標為「根據來源摘要」，第 21 回問答再用來示範檢索。不需要為此硬加向量資料庫；向量檢索不是 RAG 的必要條件。P25 講稿 `3621`「只有來源連結，能支持它查過資料」也應限定為介面的實際搜尋活動及引用；模型自行生成一個網址，不能證明執行過檢索。
- 來源：[Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks](https://arxiv.org/abs/2005.11401)。

### 13｜P43–44：Session 記憶比喻不要承諾全部永久保留

- 位置：`2150`、`2162–2169`；`3701–3703`、`3719`。
- 問題：「桌上的東西它都看得到」漏了上下文長度與壓縮；「Codex 不會永久記住你們聊過什麼」也把不會自動帶入新工作階段，和歷史保存／可恢復混為一談。新 Session 仍可能讀到舊任務留下的檔案。
- 建議：「同一 Session 通常能延續上下文；對話過長可能被摘要。`/new` 開新對話，不等於刪掉歷史或檔案。」AGENTS.md 可稱持久的專案指引，無須把產品的所有 memory 功能簡化成恰好兩層。
- 來源：[Codex CLI](https://learn.chatgpt.com/docs/cli) 的 resume 與 session 功能、[Developer commands](https://learn.chatgpt.com/docs/developer-commands) 的 `/new`、`/compact`。

## 附錄與產品版本：需要更新或重新實測

### 14｜P63：Ollama 的預設 context 與建議值已不能一概寫 4k／32k

- 位置：`3242–3254`；`3870`、`3874–3875`。
- 判定：當成現行通用教學時不正確。官方目前依 VRAM 分為 4k、32k、256k；Codex 整合頁明確建議至少 64k。32k 能完成某次測試，不能證明足夠承載其他任務；讀 21 回還會累積工具結果。
- 建議：把 32k 留作「當次實測設定」，一般建議改依所用工具及模型配置，Codex 至少 64k；記憶體評估要跟著重算。`ollama ps` 應檢查是否符合設定，不必硬性等於 32768。
- 來源：[Context length](https://docs.ollama.com/context-length)、[Codex CLI integration](https://docs.ollama.com/integrations/codex)。
- 同頁 `codex --oss` 的登入／下載問題已標成 0.154 個別實測，不能判定當時一定錯；現行官方仍有 `--oss` 及 `ollama launch codex` 路線，應標示這是當時遇到的問題，避免變成永久禁用建議。

### 15｜P62–63：本機模型門檻與大小不能由少量實測概括

- 位置：`3193`、`3214`、`3260`；`3860–3866`。
- 問題：「1B、2B 不夠用」、「4B 以下不可靠」、「最少要 gemma4:e2b」、「8 GB 不要跑」混合了當次測試結論與通用硬體門檻。速度、品質、記憶體取決於模型、量化、context、硬體及任務，沒有這個普遍參數量分界。
- 建議：「這次測過的模型中，gemma4:e2b 只達到列檔／建檔示範要求；本課不建議 8 GB 電腦使用這組設定。」`e2b` 是有效參數規格，不宜和其他模型的總參數量當成完全同一把尺。
- 官方目前 `gemma4:e2b` 頁列 7.5 GB，教材寫下載約 4.6 GB；標籤內容與封裝可能已變。保留歷史實測需加 digest／量化版本，現行下載大小須更新；不能據此直接承諾 16 GB 足夠。
- 來源：[gemma4:e2b](https://ollama.com/library/gemma4:e2b)（規格列 effective 2.3B、含 embeddings 5.1B）、[Context length](https://docs.ollama.com/context-length)。

### 16｜P37、P58：方案清單與備案入口要區分 CLI／桌面版

- 位置：`3680`；`3029–3037`、NoPlan 講稿。

- 來源：[Pricing](https://learn.chatgpt.com/docs/pricing)、[Models](https://learn.chatgpt.com/docs/models?surface=cli)。

### 17｜P61：OpenRouter 限的是 API 請求，不是每個本機工具一次

- 原文：「Codex 每呼叫一次工具就算一次」。

- 建議：「Agent 會反覆請求模型，做一個任務可能消耗多次 API 請求。」
- 額度 20／50／1000 的頁面數字，本次取得的官方文件有表格數字未正常顯示，未宣稱已全部重新確認；課前需以官方頁與帳號回傳為準。
- 來源：[OpenRouter limits](https://openrouter.ai/docs/api/reference/limits)。教材已坦白這條路尚未用真 Key 全程跑完，這是合理揭露，應保留並在課前端到端驗證。
